# Fastbot --- Архитектурный контекст

Версия: 0.1\
Статус: Архитектурная основа MVP\
Продукт: Telegram-дневник питания

## 1. Продукт и цель

Fastbot --- дневник питания в Telegram. Пользователь отправляет фото
еды, бот распознаёт предполагаемые позиции, оценивает веса и
рассчитывает нутриенты, позволяет исправить результат и сохраняет запись
только после явного подтверждения.

Fastbot **не является точным измерителем состава еды**. Распознавание и
веса являются оценками, а результаты должны быть представлены как
приблизительные.

### Основной пользовательский цикл

Фото → распознавание позиций и расчёт → правка → подтверждение →
дневник.

### MVP включает

-   распознавание позиций еды по фотографии;
-   оценку веса каждой позиции;
-   расчёт калорий и нутриентов;
-   изменение веса;
-   возможность отменить черновик;
-   явное подтверждение сохранения;
-   просмотр подтверждённых записей за день.

### Вне MVP

-   таймеры;
-   уведомления и напоминания;
-   недельная аналитика;
-   сложный food catalog;
-   автоматические рекомендации;
-   микросервисная архитектура;
-   обученная собственная CV-модель.

## 2. Архитектурные принципы

1.  **Модульный монолит.** Один deployable application, разделённый по
    слоям и доменным модулям.
2.  **AI не владеет данными.** AI выдаёт предположение; бизнес-логика
    валидирует, рассчитывает и сохраняет.
3.  **Черновик --- не дневниковая запись.** До подтверждения данные не
    появляются в дневнике.
4.  **Сохранение только по явному подтверждению.** Отмена не создаёт
    запись.
5.  **Изоляция по владельцу.** Все пользовательские операции проверяют
    `user_id`.
6.  **Расчёт воспроизводим.** Изменение веса пересчитывает нутриенты без
    повторного AI-вызова.
7.  **Снимок подтверждённых данных.** На момент сохранения фиксируются
    состав, веса и нутриенты; последующие изменения каталога/алгоритмов
    не должны незаметно менять старые записи.
8.  **Идемпотентность.** Повторный callback или нажатие Confirm не
    создаёт дубликатов.
9.  **Асинхронная обработка.** Фото-анализ не должен блокировать
    обработку Telegram-событий.
10. **Минимальная инфраструктура.** Не внедрять очереди, Redis и
    микросервисы без потребности.

## 3. Технологический стек (предлагаемый)

-   Python 3.12+
-   aiogram 3 --- Telegram Bot API
-   PostgreSQL --- постоянное хранение данных
-   SQLAlchemy 2 --- ORM/доступ к БД
-   Alembic --- миграции
-   Docker Compose --- локальный запуск и deployment
-   Telegram long polling --- MVP deployment
-   Vision-capable AI provider --- распознавание фото и
    структурированный ответ
-   Redis --- необязательный, не требуется в начальной версии

Технологии могут быть заменены, но архитектурные границы должны
сохраняться.

## 4. Компоненты

### Telegram Adapter / Bot Layer

Ответственности: - принимать Telegram update; - обрабатывать фото,
текст, команды, callback; - преобразовывать Telegram-события в вызовы
application layer; - отображать карточки черновиков и дневник; - не
содержать бизнес-правила и SQL-логику.

### Application Layer / Use Cases

Оркеструет пользовательские сценарии: - `CreateDraftFromPhoto` -
`RetryRecognition` - `EditFoodItemWeight` - `RemoveFoodItem` -
`AddFoodItemManually` (опционально для MVP) - `ConfirmEntry` -
`CancelDraft` - `GetDailyDiary`

### Domain Layer

Модели и правила предметной области: - `FoodEntry` - `FoodEntryItem` -
`Nutrition` - состояния записи; - правила редактирования и
подтверждения; - проверка весов и состава.

### Recognition Service

-   принимает фото (и необязательный текст пользователя);
-   запрашивает vision model;
-   получает структурированный список предполагаемых продуктов;
-   возвращает оценочные веса и нормализованные названия;
-   не сохраняет подтверждённые записи и не принимает решений об их
    статусе.

### Nutrition Calculator

-   рассчитывает нутриенты на основе продукта, веса и источника
    нутриентных данных;
-   не зависит от Telegram;
-   не вызывает AI при обычном редактировании веса;
-   возвращает итог по каждой позиции и по приёму пищи.

### Food Catalog / Nutrition Data

Источник нутриентов на 100 г продукта. В MVP может быть ограниченный
каталог и fallback-оценки. Если нутриентные значения приблизительные или
неизвестные, это должно быть отражено в происхождении данных/качестве
оценки, а не маскироваться под точность.

### Repositories / Persistence

-   сохраняют и извлекают пользователей, черновики, позиции и
    подтверждённые записи;
-   все пользовательские методы работают с `entry_id` вместе с
    `user_id`;
-   подтверждение выполняется транзакционно.

### Daily Diary

-   выдаёт только подтверждённые записи;
-   фильтрует по пользователю и локальному календарному дню;
-   сортирует записи по времени приёма пищи;
-   формирует дневной итог из сохранённых записей.

## 6. Главный пользовательский сценарий

1.  Пользователь отправляет фото еды.
2.  Приложение создаёт `draft` с владельцем, Telegram file id и
    временем.
3.  Бот показывает состояние «Анализирую фото...».
4.  Recognition service анализирует фото.
5.  Результат валидируется и сохраняется в черновик.
6.  Nutrition calculator рассчитывает нутриенты.
7.  Бот показывает список позиций, веса и приблизительный итог.
8.  Пользователь может отредактировать вес или удалить позицию.
9.  После редактирования расчёт обновляется без повторного вызова
    recognition.
10. Пользователь выбирает «Сохранить».
11. Use case подтверждения проверяет владельца и актуальный статус,
    пересчитывает totals и сохраняет запись атомарно.
12. Только `confirmed` записи появляются в дневнике.

Отмена переводит черновик в `cancelled` и не создаёт дневниковой записи.

## 7. Жизненный цикл записи

Основные статусы: - `draft` --- анализ выполнен/результат доступен,
запись редактируется и ещё не сохранена в дневник; - `editing` ---
необязательный временный статус UI, если он нужен; предпочтительно не
делать его обязательным для бизнес-логики; - `confirmed` --- запись
сохранена в дневнике; - `cancelled` --- пользователь отменил сценарий; -
`expired` --- необязательный статус для очистки/архивации устаревших
черновиков.

Допустимые переходы:

-   `draft → confirmed`
-   `draft → cancelled`
-   `draft → expired`
-   если UI использует `editing`: `draft → editing → draft`, затем
    `draft → confirmed/cancelled`.

Статус Telegram FSM не является источником истины. Источник истины ---
запись в БД. FSM хранит только контекст взаимодействия, например, какой
item сейчас выбран для ввода веса.

## 8. UX и Telegram UI

Предпочтительный UX: - одна карточка draft-сообщения, обновляемая через
edit message; - inline-кнопки: «Изменить», «Сохранить», «Отмена»; - в
режиме редактирования выбор позиции и ввод нового веса; - после
изменения показывать обновлённый состав и расчёт; - не создавать большое
количество сообщений без необходимости.

Старая callback-кнопка должна безопасно обрабатываться: проверка
владельца, состояния draft и валидности действия. Если draft уже
обработан, сообщить пользователю, что он больше не доступен для
редактирования.

Callback payload содержит короткое действие и идентификатор
записи/позиции, но не полные данные еды или нутриентов. Не доверять
payload без проверки в БД.

## 9. Recognition: контракт результата

Recognition принимает изображение и, если есть, текстовый контекст
пользователя. Возвращает структурированный результат, например:

``` json
{
  "items": [
    {
      "name": "Cooked rice",
      "estimated_weight_g": 150,
      "recognition_note": "Estimated from visible portion"
    },
    {
      "name": "Chicken breast",
      "estimated_weight_g": 120,
      "recognition_note": "Estimated"
    }
  ]
}
```

Требования: - AI-результат считать недоверенным входом; - валидировать
JSON/schema, названия, вес, диапазоны и пустые результаты; - не выдавать
оценку за точное измерение; - не допускать отрицательные или
нереалистичные веса; - предусмотреть повтор анализа при технической
ошибке; - сохранять исходный результат/метаданные оценки только если это
полезно для отладки и privacy policy позволяет.

Recognition не отвечает за запись в дневник и не меняет статус на
`confirmed`.

## 10. Расчёт нутриентов

Нутриенты рассчитываются по значениям на 100 г:

`nutrient_total = nutrient_per_100g × weight_g / 100`

Расчёт выполняется детерминированным сервисом. При редактировании веса
меняются totals соответствующей позиции и общие totals.

Рекомендуемые поля: - calories; - protein; - fat; - carbohydrates.

Если каталог не содержит продукт, допускается fallback-оценка. Источник
значений следует сохранять (например, `catalog`, `estimated`, `manual`)
и показывать приблизительный характер результата.

## 11. Модель данных (предварительная)

### users

-   `id` UUID, primary key
-   `telegram_id` BIGINT, unique, not null
-   `timezone` TEXT, optional/default
-   `created_at` TIMESTAMPTZ

### food_entries

-   `id` UUID, primary key
-   `user_id` UUID, FK → users, not null
-   `status` --- draft/confirmed/cancelled/expired
-   `source` --- например, photo
-   `photo_file_id` --- Telegram file id, nullable
-   `eaten_at` TIMESTAMPTZ
-   `created_at` TIMESTAMPTZ
-   `confirmed_at` TIMESTAMPTZ, nullable
-   totals: calories, protein, fat, carbohydrates
-   при необходимости recognition metadata

### food_entry_items

-   `id` UUID, primary key
-   `entry_id` UUID, FK → food_entries, not null
-   `name` TEXT
-   `weight_g` NUMERIC
-   нутриенты item: calories, protein, fat, carbohydrates
-   `nutrition_source` / `data_source`
-   при необходимости reference на каталог

Итоги и позиции подтверждённой записи хранят snapshot данных на момент
подтверждения. Схема может уточняться при реализации; не создавать
дополнительные сущности без конкретной потребности.

## 12. Изоляция пользователей и авторизация

Telegram ID связывается с внутренним `users.id`. Внутренний UUID
использовать в таблицах.

Каждая операция чтения, редактирования, отмены или подтверждения должна
быть scoped по `user_id`.

Пример repository contract:

`get_entry(entry_id, user_id)`

Не использовать небезопасный доступ вида `get_entry(entry_id)` в
пользовательских сценариях без проверки владельца.

Правила: - entry id из callback не является доказательством доступа; -
при запросе чужой записи не раскрывать её содержимое; - все
update/delete/confirm операции проверяют ownership; - пользовательские
данные изолированы по owner foreign key; - секреты и API ключи хранятся
в env/secrets, не в репозитории; - ограничивать размер/тип входного
файла; - не помещать содержимое фото и приватные данные в технические
логи без необходимости.

## 13. Подтверждение и транзакционность

Confirm use case должен: 1. получить запись по `entry_id + user_id`; 2.
проверить, что статус допускает подтверждение; 3. защититься от
конкурентного/повторного confirm (row lock или условное обновление); 4.
пересчитать итог из актуальных items; 5. записать totals и
`confirmed_at`; 6. установить `confirmed`; 7. завершить транзакцию.

Повторное подтверждение не создаёт дубликат. Отмена не создаёт
дневниковую запись. Diary query возвращает только confirmed.

Пример логики (псевдокод):

``` python
async def confirm_entry(entry_id, user_id):
    async with db.transaction():
        entry = await repo.get_for_update(entry_id, user_id)

        if entry.status != "draft":
            return AlreadyProcessed

        totals = calculator.calculate(entry.items)
        await repo.update_totals(entry.id, totals)
        await repo.mark_confirmed(entry.id)

    return Success
```

Реализация должна гарантировать атомарность изменений, а не полагаться
только на UI-кнопку.

## 14. Редактирование

MVP editing: - выбрать позицию; - ввести новый вес в граммах; -
валидировать положительное число и разумный диапазон; - пересчитать
нутриенты; - обновить карточку draft.

Дополнительно/по приоритету: - удалить позицию; - добавить позицию
вручную (если это не увеличивает критично scope).

Редактирование не вызывает повторный Vision API. Отмена draft не создаёт
запись. Подтверждённые записи в MVP не редактируются, если отдельный
сценарий редактирования после сохранения не был запланирован.

## 15. Дневник за день

Diary query: - ограничивает выборку `user_id`; - выбирает только
`status = confirmed`; - фильтрует по локальному календарному дню
пользователя; - сортирует по `eaten_at`; - отображает записи, items и
totals.

Дата приёма пищи хранится в `TIMESTAMPTZ` (UTC). Границы дня вычисляются
в timezone пользователя и преобразуются в UTC. В первой версии timezone
может быть задана по умолчанию; настройка timezone в интерфейсе
необязательна для MVP.

Дневной итог агрегируется из confirmed entries. Draft/cancelled/expired
не учитываются.

## 16. Обработка фото и отказоустойчивость

Первый MVP допускает обработку без отдельной очереди: - принять фото; -
создать draft; - отправить «Анализирую»; - выполнить async
recognition; - сохранить результат; - обновить Telegram-карточку.

При росте нагрузки можно вынести recognition в worker/queue, сохранив
application service contracts.

Обработать: - timeout AI; - недоступность provider; - невалидный
JSON/schema; - пустое/непонятное изображение; - повторную попытку; -
повторное фото; - отправку нескольких фото подряд; - устаревший
callback; - повторный Confirm; - ошибку Telegram edit message.

Draft должен оставаться восстановимым после рестарта приложения. Сбой
recognition не должен превращать draft в confirmed.

## 17. Время и timezone

-   Время хранить в UTC (`TIMESTAMPTZ`).
-   Для дневника использовать локальные границы календарного дня
    пользователя.
-   `eaten_at` --- время еды, по умолчанию время отправки фото; в
    будущем пользователь может корректировать время, но это не
    обязательный MVP.
-   Не использовать server timezone для определения пользовательского
    «сегодня».

## 18. Deployment и инфраструктура

MVP: - один VPS/host; - Docker Compose; - приложение Fastbot; -
PostgreSQL; - Telegram long polling; - автоматический restart; -
env/secrets; - регулярные backups; - базовый мониторинг ошибок и health
checks.

Не требуется изначально: - Kubernetes; - микросервисы; - webhook (можно
рассмотреть позже); - Redis/Celery; - сложная event streaming
инфраструктура.

## 20. Этапы реализации

1.  **Foundation:** конфигурация, aiogram, PostgreSQL, миграции, user
    identity, Docker.
2.  **Photo → draft:** получение фото, recognition adapter, schema
    validation, сохранение draft.
3.  **Nutrition:** catalog/estimate, calculator, totals.
4.  **Editing UX:** выбор item, изменение веса, пересчёт.
5.  **Confirm/cancel:** атомарное подтверждение, защита от повторов,
    cancellation.
6.  **Diary:** дневной список и агрегаты confirmed entries.
7.  **Hardening:** обработка ошибок, ownership tests, logs, backup,
    deploy.

## 21. Критерии готовности MVP

MVP считается готовым, когда: - пользователь отправляет фото и получает
распознанные позиции; - видит приблизительные веса и нутриенты; - может
исправить вес; - изменение веса приводит к пересчёту без повторного
AI; - может отменить черновик; - отменённая запись не появляется в
дневнике; - только explicit confirm создаёт confirmed запись; -
повторное confirm не создаёт дубликат; - дневник показывает записи за
день; - пользователь не может получить доступ к чужой записи; - черновик
сохраняется при перезапуске бота; - AI/Telegram ошибки обрабатываются
без потери или ошибочного подтверждения данных.

## 22. За пределами MVP / будущие расширения

Потенциальные расширения, не влияющие на базовую архитектуру: - более
полный каталог еды; - улучшение распознавания и источников нутриентов; -
добавление еды текстом; - редактирование подтверждённых записей; -
timezone настройки; - недельная аналитика; - напоминания; - очередь
обработки AI; - сохранение изображений в отдельное хранилище; -
история/аудит изменений.

## 23. Ключевой принцип продукта

AI делает предположение о том, что изображено на фото. Пользователь
проверяет и исправляет предположение. Расчёт является ориентировочным.
Только после явного подтверждения пользователя запись фиксируется в
дневнике.

**Fastbot должен быть удобным журналом с AI-помощью, а не системой,
которая выдаёт оценки AI за точные измерения.**
